# Full i18n Pass — Exports, Proposal Detail, Landing Page, and i18n Skill

**Date:** 2026-02-04
**Branch:** frontend-v2

## Summary

Comprehensive internationalization pass across the app's major surfaces: export files (MD/CSV/JSON), the proposal detail page, the voting records list, and the landing page governance table. Also created a reusable i18n skill to streamline future translation work. The session revealed important project conventions about what to translate vs. keep in English.

## What Was Done

1. **Localized export files** — Added `ExportLabels` typed interface to `exportRationales.ts`, updated `exportToMarkdown()`, `exportToCSV()`, and `exportToJSON()` to accept localized labels and locale parameter. Added UTF-8 BOM to CSV for Excel compatibility. Created `translateVoteValue()` helper and `translateVotesForExport()` async batch translator via DeepL API.

2. **Added `"export"` namespace** (21 keys) to all 7 locale files for export file labels (headings, column headers, vote values).

3. **Localized proposal detail page** (`[hash].tsx`) — Extracted 44+ hardcoded strings into the `"proposal"` namespace. Covers: page headings, donut chart titles, vote breakdown labels, threshold labels, voting trend labels, detail tab fields, share button, and more.

4. **Added `"proposal"` namespace** (44 keys) to all 7 locale files with full translations for German, French, Spanish, Portuguese, Japanese, and Chinese.

5. **Translated Yes/No/Abstain in VotingRecords** — Added `translateVote()` helper that maps English API values to localized display text while preserving original values for badge styling.

6. **Fixed DRep Votes donut chart title** — Was hardcoded while CC Votes and SPO Votes already used translations. Changed to `tProposal("drepVotes")`.

7. **Translated "Share on X" button** — Added `shareOnX` key to `"proposal"` namespace in all 7 locale files.

8. **Partial i18n of GovernanceTable.tsx** — Translated table headers, "Not Eligible" donut center text, "Show more proposals" buttons, and view toggle aria-labels. Intentionally kept filter dropdowns and row content (action types, status) in English per user preference.

9. **Made voting trend role filter language-aware** — Role filter dropdown labels and segment labels on the voting trend chart now respond to the user's locale.

10. **Created i18n skill** (`.claude/skills/i18n/`) — Comprehensive skill documenting all 23 namespaces, 4 wiring patterns (direct hook, API value mapping, typed labels for utils, locale-aware formatting), project conventions, and common mistakes.

## Key Learnings

### User preferences about translation scope matter
The user explicitly wanted filter dropdowns and action type/status on landing page proposal cards to stay in English. This was discovered through an iterative back-and-forth where we first translated everything, then reverted specific items. Always clarify scope upfront.

### Two-tier translation for exports
Static labels (headings, headers) use `next-intl` translation files while dynamic content (rationale text) requires runtime translation via DeepL API. These are fundamentally different concerns.

### Pure utility function translation via typed labels
Functions in `lib/` can't use React hooks. The `ExportLabels` interface pattern keeps utilities pure and testable while enabling full localization.

### Badge/styling logic must use original English values
When translating display text like "Yes"/"No"/"Abstain", the original English value must still be passed to styling functions (`getVoteBadgeClasses`). Only the rendered text should be translated.

### Iterative i18n is normal
Translating a large app is incremental. Having a skill that documents existing namespaces and patterns dramatically speeds up subsequent passes.

### UTF-8 BOM is essential for CSV i18n
Without `\uFEFF` prefix, Excel garbles non-ASCII characters. Single character fix but critical.

## Patterns Discovered

### Selective i18n — translate display, keep logic English

```typescript
// Display: translated
<span>{translateVote(vote.vote)}</span>

// Logic: original English value
<Badge className={getVoteBadgeClasses(vote.vote)}>
  {translateVote(vote.vote)}
</Badge>
```

### Project convention: what stays English

- Landing page filter dropdown labels and items
- Action type and status values on proposal cards (landing page)
- JSON export keys and enum-like values
- Technical identifiers (DRep, SPO, CC, ADA)

### Async export with translation loading state

```typescript
const [isExporting, setIsExporting] = useState(false);

const handleExport = async (format: string) => {
  setIsExporting(true);
  try {
    const translatedVotes = await translateVotesForExport(votes, locale);
    // ... export using translatedVotes
  } finally {
    setIsExporting(false);
  }
};
```

## Decisions Made

| Decision | Rationale |
|----------|-----------|
| Keep filter dropdowns in English | User preference — these are technical domain labels |
| Keep action type/status on cards in English | User preference — consistent with filter labels |
| Translate table headers but not row content | Headers are structural UI; row content is domain data |
| Create dedicated i18n skill | Recurring task needs standardized approach |
| 44 keys in "proposal" namespace | Covers all 5 tabs of proposal detail page |
| Separate "export" namespace from UI namespaces | Export labels are fundamentally different from UI labels |
| Batch translation in groups of 5 | Balance between speed and API rate limiting |
